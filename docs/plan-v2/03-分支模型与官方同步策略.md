# 03 · 分支模型与官方同步策略

> 前置阅读：[02-目标与总体方案](02-目标与总体方案.md)。本文是 Git 操作的**唯一权威规范**，ORCH/GIT 必须逐字执行；开发角色只需读 §1、§6、§7。

---

## 1. Remote 与分支命名（终态）

### 1.1 Remote

| remote | URL | 用途 | 红线 |
|---|---|---|---|
| `upstream` | `https://github.com/deepseek-ai/deepseek-harness.git` | 只 fetch（已配置） | **永远不 push** |
| `origin` | `https://github.com/zsagi1368/deepseek-harness-DSH.git` | fork 远程 | URL **不得内嵌凭据**（用凭据管理器，见 §7） |

### 1.2 分支模型

```
upstream/master ──fetch──▶ 本地 upstream/master
                              │ git merge --ff-only（每周 ≥1 次，SOP 见 §4）
                              ▼
                      master（本地=origin/master，官方历史的纯镜像）
                              │ 从 master 切出
                              ▼
                      our/v2（DSH 主线，长期分支）
                       ├── our/feat/<topic>   功能分支（our/feat/plugin-governance 等）
                       ├── our/fix/<bug-id>   修复分支（our/fix/p1-max-tokens-truncation 等）
                       └── our/release/<ver>  发布固化分支
                      archive/<name>          归档分支（archive/our-base-v1 等，只增不改）
                      backup/<date>-<desc>    同步前快照（backup/20260822-pre-v2 等）
```

命名规则：全小写 kebab-case；bug-id 用统一编号（见 §6 问题编号）；topic 名与任务 ID 对应（如 `our/feat/T2-1-plugin-governance`）。

### 1.3 各分支的内容纪律

- `master`：**零本地提交**，只做 `git merge --ff-only upstream/master` 后 push。任何 DSH 改动不得落在 master。
- `our/v2`：只接受来自 `our/feat/*`、`our/fix/*` 的 merge（`--no-ff`，保留分支拓扑）或 rebase 后的 fast-forward；**禁止直接在 our/v2 上堆日常提交**（发布固化与小 chore 除外）。
- 功能/修复分支：生命周期 = 单个任务（04 号文档的任务粒度），合入即删（删除前确认已在 our/v2）。
- `archive/*`、`backup/*`：只增不改不删。

## 2. 一次性重建程序（Phase 1 执行，任务书见 07）

> 目标：在不丢失任何本地工作的前提下，把开发主线切回官方真实历史上。**本节是唯一一次的特殊操作，此后永远走 §4 的常规 SOP。**

### 2.1 前置（Phase 0 完成的标志）

工作区干净（构建产物噪音已按 07 号文档 T1.1 方案处置）、stash 已处置、`_tmp_*` 已删、所有旧分支已打 backup。

### 2.2 重建 our/v2（在 Fork 仓库内）

```bash
# 0) 确认 upstream 最新
git fetch upstream --tags --prune

# 1) 建备份（对应旧线，永不再动）
git branch backup/20260822-pre-v2 our/base

# 2) 提取本地增量补丁集（详见 07 号文档 T1.2，产物：Plan/artifacts/ 下的三清单 + 补丁文件）
#    新增清单 add.list / 修改清单 mod.list / 删除清单 del.list（del 一律否决）

# 3) 建新主线与官方祖先
git checkout -b our/v2 upstream/master

# 4) 应用新增清单（整目录搬移，排除 junk —— 详见 T1.2）
git checkout our/base -- <add.list 中的路径>

# 5) 应用修改补丁（对官方文件的小改动，三方合并）
git diff dsh-v0.1.0-rc.8 our/base --ignore-cr-at-eol -- <mod.list 路径> | git apply -3 -

# 6) 逐文件裁决冲突（官方 0.1.1 大改区：credentials/core-session/core-tools/llm，裁决表见 T1.3）
#    冲突裁决优先级：官方 security/bugfix > 本地实现 > 本地文档
```

### 2.3 铺设 master 为官方镜像（无 force push）

> 2026-08-22 更新：origin 仓库已被误删并按 [13-GitHub仓库重建与活跃记录保留方案](13-GitHub仓库重建与活跃记录保留方案.md) 以**全新真 fork** 重建。远程是空白的 → master 无需任何 force push，直接铺正确内容。

```bash
# 前置：R1–R4 完成（新 fork 已建立、本地 origin 已指向它、存量分支已推送）
git checkout master && git reset --hard upstream/master
git push origin master                # 全新远程上的首次推送，非覆盖任何他人历史
```

若本地旧 master（孤儿快照 9006243d87）尚未归档，先 `git branch archive/old-master-snapshot master` 保底。

### 2.4 归档与清理

- `git branch -m our/base archive/our-base-v1`（或新建 archive 分支后保留 our/base 至用户确认删除）；
- 推送 archive/*、backup/* 到 origin（`git push origin --set-upstream`）；
- 旧 tag 不动；新 tag 只按 §5 规则打。

## 3. 差异追踪（长期机制）

- **单一事实源**：`docs/dsh/CHANGELOG.md`（每条含任务 ID、提交号、动机）＋ 04 号文档的任务表。
- **机器可核对**：`scripts/diff-with-official.sh`（R&D 已有设计，随 P3 落地为仓库内脚本）——输出 `our/v2` 与 `upstream/master` 的净差异（排除版本号行与 docs/dsh/）；
- **移植检查**：官方每次发布后，对官方 release notes 与我们的 CHANGELOG 做双向核对：官方修了我们也修的 → 标记"可弃本地补丁"；官方改了我们补丁依赖的接口 → 触发 §4 冲突流程。

## 4. 常规同步 SOP（此后每周至少一次，或官方发版当天）

```bash
# 1) 全备份
git fetch upstream --tags --prune
git branch backup/$(date +%Y%m%d)-pre-sync our/v2

# 2) 镜像 master（纯快进）
git checkout master
git merge --ff-only upstream/master
git push origin master

# 3) 同步开发主线
git checkout our/v2
git merge master                      # 常规合并；冲突走下面规则
# 冲突裁决优先级：① 官方 security/bugfix ② 官方公共 API 变更（跟随）③ 本地功能实现（保留意图、适配新 API）
# 冲突解决后必须：pnpm install && pnpm build && pnpm test && pnpm check:all（Windows 子集）

# 4) 处理官方语义冲突（本地补丁被官方等价实现取代 → 删本地补丁，CHANGELOG 记"adopted upstream <commit>"）

# 5) 版本与记录
#    按 VERSION-NAMING-SPEC bump：0.1.1-rc.2-DSH<date><letter>；CHANGELOG 增"Sync"条目（官方区间 commit range + 处理摘要）
# 6) push our/v2 + archive 检查
```

**同步完成的定义**：全门禁绿 + CHANGELOG Sync 条目 + STATE.md 更新 + `scripts/diff-with-official.sh` 输出与预期基线一致。

## 5. 版本与 tag 纪律

- 版本格式 `<官方版本>-DSH<YYYYMMDD><a-z>`（VERSION-NAMING-SPEC）；**基线官方版本必须与合并进的 upstream 一致**（现在是 0.1.1-rc.2）。
- bump 手段：根 `package.json` 的 `scripts.version`（官方提供），一次改动全仓库统一；**禁止手改散包版本**。
- tag 规则：`v<完整版本号>`；只能打在通过 `pnpm check:all`（Windows 子集）与全部测试的 our/v2 提交上；打 tag 的同时更新 docs/dsh/CHANGELOG（同提交）。修复历史教训：tag 滞后顶端 8 提交的事故不得再发生。

## 6. 问题编号统一（跨 git/issue/文档）

采用单一新编号 `DSHV2-<序号>` 登记 04 号文档任务与运行中发现的新问题；与旧四套编号的映射表由 T4.2 建立：`E-xxx / DSH-xxx / ISSUE-xxx / BUG-xxx ↔ DSHV2-xxx`。分支命名中的 bug-id 一律用 DSHV2 编号。

## 7. 本机 Git 配置规范（Windows）

```bash
git config user.name  "zsagi1368"                          # 或你惯用昵称（统一身份，修 C-4 双身份问题）
git config user.email "<你的 GitHub 账号已关联邮箱>"        # ⚠️ 见下：贡献图按作者邮箱记账
git config core.autocrlf false                          # EOL 全部交给官方 .gitattributes（重建后随基线恢复）
git config commit.gpgsign false                         # 如需签名另议
# 凭据：删除 remote URL 内嵌 token，改用凭据管理器
git remote set-url origin https://github.com/zsagi1368/deepseek-harness-DSH.git
# 首次 push 时由 Git Credential Manager 弹窗存凭据；或 gh auth login
```

**邮箱规则（2026-08-22 修订，原因：贡献图）**：GitHub 贡献图按**提交作者（author）邮箱**关联账号——旧线混用 `dsh-team@zsagi.us.ci`/`zsagi1368@gmail.com`/旧式 noreply，多半没记上账。今后统一：`user.email` 填 Settings→Emails 里**已验证的邮箱或你账号的 noreply 地址**；团队署名改走提交尾注 `Signed-off-by: DSH Team <dsh-team@zsagi.us.ci>`（CODING-STANDARDS 本就要求），不再用 author 字段承载。

禁止事项：任何形式的 token 写入 remote URL / 脚本 / 文档 / 提交；`git push --force`（只允许 `--force-with-lease` 且仅在 §2.3 批准场景）；跳过 backup 直接在 our/v2 上做试验性 reset。
