# 05 · Agent 团队组建与编排方案

> 本文回答两件事：**怎么组建队伍**（§2–§4）与**怎么编排运转**（§5–§8）。任何协调者（人或 ORCH Agent）照此即可拉起并驱动整个项目。

---

## 1. 编排总原则

1. **单一协调者（ORCH）**：只有 ORCH 对用户说话、维护状态板、做调度决策；其余角色只与 ORCH 交互（星型拓扑，避免代理间网状对话失控——旧开发"6 份 FINAL 报告互相矛盾"的教训）。
2. **任务书驱动**：每次派发的最小完整上下文 = 对应任务书全文（06–09）＋ 10 号文档 ＋ 该任务的输入物路径。任务书必须自包含，不依赖会话记忆。
3. **包级互斥**：同一包目录同时只有一个代理可写（04 §2）；跨包任务才并行。
4. **阶段门禁**：Phase 门禁（G0–G5）由 REV 独立验收，ORCH 不得自验自过。
5. **全程留痕**：每个任务一份交接记录（§7），最终汇总成交付报告——修复"声称与事实不符"的旧问题（A-2/B-7）。

## 3. 组建方式（ZCode / 多代理环境的具体做法）

- **ORCH = 主会话**：不另 spawn。启动指令见 Plan/README.md §4。
- **其余角色 = 按需 spawn 的子代理**（ZCode Agent 工具；Claude Code 等环境用对应 subagent 机制）。两种组织模式：
  - **轻量模式（默认）**：角色不常驻，按任务 spawn"一次性执行代理"，提示词 = 角色章节（§4 对应小节）＋任务书＋10 号文档。适合本项目的任务粒度。
  - **常驻模式**：长任务（T2.3/T2.6/T2.7/T2.8）可 spawn 后台常驻代理，用 SendMessage 驱动多轮，减少重复灌输上下文。
- **并行上限 3**（含 ORCH 自身执行的小任务则 ≤2 个子代理），受包级互斥约束。
- **人类用户**的三个保留决策点（ORCH 必须停下询问，不得代办）：① PAT 轮换的 GitHub 操作与确认（T0.1）；② origin/master 是否 force push（03 §2.3 方案 A/B）；③ 最终 push 与发布（T5.3 前确认）。

## 5. 状态板（`Plan/STATE.md`，ORCH 维护，每次调度后更新）

```markdown
# STATE — 更新时间 / 当前 Phase / 门禁状态（G0..G5: ✅❌🔒）
| 任务 | 状态(todo/doing/blocked/done) | 负责角色 | 分支 | 交接记录 | 备注 |
|---|---|---|---|---|---|
| T1.2 | done | ARCH | — | logs/TASK-T1.2.md | 裁决表 3 项 drop |
## 冲突区占用
packages/plugins/** → DEV-PLUGIN（至 M2）
## 阻塞与升级
（空）
```

配套目录：`Plan/logs/TASK-<ID>.md`（交接记录）、`Plan/artifacts/`（中间产物：清单、裁决表、补丁）。

## 6. 编排流程（一个任务的完整生命周期）

```
ORCH 选任务（依赖满足＋包无占用）
 → 组装派发包（角色章节+任务书+10 号+输入物路径）
 → spawn 子代理（或派给自己）→ 执行 → 产出物 + 交接记录
 → ORCH 核对产出物存在性 → 指派 REV 验收（对照任务书"验收标准"逐条）
 → 通过：更新 STATE.md；失败：退回重做（附 REV 意见），同一任务退回 ≥2 次触发 §8 升级
 → 阶段末：REV 做门禁验收（G*）→ 过门才开下一 Phase
```

## 7. 交接协议（任务完成的唯一凭证）

`Plan/logs/TASK-<ID>.md` 必含六节，缺一不视为完成：
1. **结论**：一句话（做了什么/结果）。
2. **证据**：分支名、提交号列表（`git log --format='%h %s'`）、测试输出摘要（命令+结果行）。
3. **改动清单**：`git diff --stat` 摘要（新增/修改/删除文件数与关键路径）。
4. **决策记录**：所有偏离任务书的决定及理由（如裁决 drop 了某文件）。
5. **遗留与风险**：未尽事项、给下游任务的提示。
6. **验收对照**：任务书验收标准逐条 ✅/❌。

## 8. 失败处理与升级路径

| 情形 | 处理 |
|---|---|
| 门禁/测试红 | 退回执行者修复；连续 2 次失败 → ORCH 换代理或亲自介入；根因属设计 → 召 ARCH |
| git 冲突不可解（T1.3 裁决表外） | 停下，ARCH+GIT 会诊，必要时请示用户（保留官方优先原则） |
| 发现新的安全泄露 | SEC 可直接叫停推送；ORCH 通报用户；插入临时 T0.x 任务 |
| 官方突然发新版（0.1.1-rc.3+） | 不中断当前 Phase；在最近的同步窗口按 03 §4 SOP 处理；若与 P2 改动强冲突（credentials/llm 再大改），ORCH 决定是否提前同步 |
| 范围蔓延（如 memory 包"顺手做掉"） | 一律进 backlog-00x，不得插入当前 Phase |
| 代理上下文耗尽/中断 | 任务书可重入：新代理从交接记录+STATE.md 无损接手（这就是任务书自包含的原因） |

## 9. 例行节奏

- 每任务完成 → 更新 STATE.md（ORCH）。
- 每门禁通过 → 向用户简报（里程碑 + 证据摘要）。
- 每日（或每 8 个任务）→ 全量 `git status`/分支清点，防漂移。
- 官方同步窗口：每周一（或官方发版日），见 03 §4。
