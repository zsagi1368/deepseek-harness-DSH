# 09 · 任务书 — Phase 3/4/5：质量体系、文档整合、发布验收

## Phase 3 · 质量体系恢复

### T3.1 治理 CI 修复与工作流核验（QA，M）

**目标**：push 后官方 18 个 workflow + 1 个治理 workflow 全绿。

**步骤**：
1. 确认坏 CI 已随基线消失（`plugin-compat.yml` 在 T1.2 裁决为 drop，不随 our/v2 存在）。
2. 新建 `.github/workflows/plugin-governance.yml`（对齐官方 workflow 风格：读 `ci.yml` 的 checkout/setup/pnpm 缓存写法）：
   - 触发：push/PR 涉及 `packages/plugins/**`、`packages/host/plugin-governance/**`、`packages/client/ui-plugin-manager/**`；
   - 步骤：`pnpm install --frozen-lockfile` → 定向测试 `pnpm vitest run packages/plugins/plugins packages/host/plugin-governance`（**不要**用 `pnpm test --filter=` 这种 pnpm/vitest 混用语法——旧 CI 的错误）→ typecheck。
3. 官方 18 个 workflow 逐个过目一遍触发条件是否需要 DSH 调整（预期不需要）；fork 仓库 GitHub 侧缺少官方 org 的 secrets/runner 的（如 e2b、wine 门），在 STATE.md 记录"环境性不可达"清单，不修改 workflow。
4. push 后盯首轮 Actions 结果，逐红修复。

**验收**：GitHub Actions 全绿（或"环境性不可达"清单有据且经 REV 认可）；新 workflow 的定向测试确执行了治理包用例（Actions 日志为证）。

### T3.2 lint/工具链断链修复（QA，S）

**目标**：官方质量工具在本仓库全部可用。

**步骤**：核验 `.oxlintrc.json`、`.oxlintrc.staged.json`、`.jscpd.json`、`.editorconfig`、`.gitattributes`（upstream 自带，随 our/v2 存在）；跑 `pnpm lint`、`pnpm duplication`、`git config core.autocrlf false` 后 `git status` 干净；lefthook 重装 `node scripts/install-lefthook.mjs`，验证 pre-commit 翻译配对/staged lint/whitespace 检查生效（做一次试验提交）。

**验收**：上述命令全绿；试验提交触发且通过 hooks；i18n merge driver 配置（`.gitattributes` 内含官方驱动声明）就位。

### T3.3 hygiene 与覆盖门对齐（QA，M）

**目标**：`pnpm hygiene` 与覆盖门纳入治理包。

**步骤**：跑 `pnpm hygiene`（rescope-vendor/knip/publint/constraints/verify-* 全家）；修复因新增包引入的失败（典型：constraints 对新包的约束、verify-package-invariants、 THIRD_PARTY_NOTICES 若引入新依赖需再生 `gen-third-party-notices`）；把治理包纳入 `test:coverage` 口径（Windows 按官方 Windows 门子集）。

**验收**：`pnpm hygiene` 全绿；覆盖报告含治理包并达标；THIRD_PARTY_NOTICES 更新（如需）。

### T3.4 diff-with-official 脚本落地（QA，S）

**目标**：净差异可持续核对（03 §3 的机器化）。

**步骤**：写 `scripts/diff-with-official.mjs`（Node，跨平台；参照旧 `diff-with-official.sh` 思路）：`git diff upstream/master...our/v2 --stat --numstat`，排除版本号行与 `docs/dsh/**`，输出人读摘要 + `docs/dsh/diff-baseline.txt` 基线；README 简述用法；脚本自身加进官方 scripts 测试体系（如官方 scripts 有 spec 惯例则补最小 spec）。

**验收**：`node scripts/diff-with-official.mjs` 可运行，输出与 04 号任务表预期改动面一致；基线文件入库。

## Phase 5 · 发布与验收

### T5.1 版本统一与发布分支（GIT，S）

**步骤**：`git checkout -b our/release/0.1.1-rc.2-DSH$(date +%Y%m%d)a our/v2`；用官方 `pnpm run version` 机制 bump（或按其 scripts.version 实际入口执行）统一全仓库版本；CHANGELOG 补版本头；全门禁复跑。

**验收**：`git grep '"version"' -- package.json apps/*/package.json` 抽查一致；tag 规则满足 03 §5。

### T5.2 最终审计与 tag（REV+SEC，M）

**步骤**：REV 按 02 §5 七条逐项验收并留证据；SEC 复核：`grep -rn "ghp_"` 零命中、无新增危险调用（exec/eval 面）、THIRD_PARTY_NOTICES 一致、`.git/config` 无凭据；全绿后 `git tag v<版本> && git push origin v<版本>`（tag 打在 release 分支通过门禁的提交上）。

**验收**：审计清单 100% ✅（任何 ❌ 退回对应 Phase）；tag 与提交对应关系写入交接记录。

### T5.3 推送与远程布局确认（GIT，S，用户确认点）

**步骤**：`git push origin our/v2 our/release/*`；确认 GitHub 默认分支=our/v2；与用户确认是否执行方案 A（master force push 成官方镜像，03 §2.3 流程）；archive/backup 分支最终清点。

**验收**：远程分支/tag 与 STATE.md 清点一致；用户对远程布局的确认记录在案。

### T5.4 最终报告与 STATE 收口（ORCH，S）

**步骤**：写 `docs/dsh/DELIVERY-v2.md`（三元组）：目标达成对照（02 §5）、全部任务提交号索引（汇总各交接记录）、backlog 终表、同步 SOP 指针；STATE.md 标记全部 done 并归档为 `Plan/logs/STATE-final.md`；向用户交付总结。

**验收**：报告中每一条结论都有提交号/测试输出背书；无"声称无证据"条目（与旧报告的根本区别）。

### T5.5 同步 SOP 演练（GIT，S）

**步骤**：模拟/真实执行一次 03 §4：fetch upstream（若官方有新提交则真实合并，否则 dry-run 记录每步命令与预期）；把实际遇到的坑回写 03 号文档修订版。

**验收**：SOP 全流程可执行；03 号文档按演练结果修订；STATE.md 收口。
