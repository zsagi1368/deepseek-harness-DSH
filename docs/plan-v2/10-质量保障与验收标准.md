# 10 · 质量保障与验收标准

> 所有执行角色的共同约束。与任务书冲突时，以"更严者"为准；与官方 AGENTS.md/CODING-STANDARDS 冲突时以官方为准。

---

## 1. 代码标准（继承 R&D/CODING-STANDARDS.md + 官方 AGENTS.md，要点）

1. **官方架构铁律优先**：一切皆 Cordis 插件；注册必须 `ctx.effect()`；瀑布监听必须 `next()`；model-visible ⟺ logged；strict TS + JSDoc 契约；`test:coverage` 是门禁；vendored 包（`vendor/**`）**只读**。
2. 文件头注释（fork 新增文件）：`@module / @author DSH Team / @license MIT / @since <版本>`；注释**禁止**出现个人信息、本地路径（`C:\Users`、`/home/`、`G:\` 等）、调试残留、AI 生成痕迹。
3. 命名：文件 kebab-case；类 PascalCase；导出函数/常量 camelCase 或 UPPER_SNAKE。包名 `@deepseek-ai/dsh-<name>`。
4. 格式交 oxlint（`pnpm lint`）；2 空格缩进、行长 100。
5. TS 纪律：**禁 `as any`**（历史审计发现 132 处 `!.` 断言，移植时不新增）；未处理 Promise 禁止（26 处历史债不扩大）；异步必须可观测（错误上抛或记录）。
6. 提交信息：`<type>: <description>`（feat/fix/docs/style/refactor/test/chore），正文说明动机，尾注 `Signed-off-by: DSH Team <dsh-team@zsagi.us.ci>`；**提交内容必须与标题一致**（旧线"空提交冒充修复"是硬教训）。
7. 非平凡变更必须附 Agent Note（`.agents/notes/implemented/`，格式对照官方现有 notes）。

## 2. 测试要求

| 项 | 标准 |
|---|---|
| 收集 | 必须落在官方 vitest glob：`packages/*/*/tests/**/*.spec.ts`；测试文件命名 `*.spec.ts` |
| 覆盖 | 官方 per-file 100% 门；豁免仅限 `/* v8 ignore ... */` + 原因注释，且交接记录列明 |
| 缺陷修复 | 每个 bug 修复自带回归测试（先红后绿） |
| 移植代码 | 每个安全移植项有对应 spec；治理包核心路径（registry/guards/sandbox/persistence/adapter）全覆盖 |
| UI | web 冒烟用例进 `vitest.web` 体系；不留仅手测的路径 |
| 脚本 | `scripts/` 新增 Node 脚本跨平台（`.mjs`，不依赖 bash-only 特性），有最小用法说明或 spec |

**门禁命令**（本地必须绿再提交）：`pnpm install && pnpm build && pnpm typecheck && pnpm test && pnpm lint`；涉及包结构再跑 `pnpm knip --treat-config-hints-as-errors` 与 `pnpm hygiene`；文档改动跑 `pnpm run verify-translation-pairing`。Windows 环境对 `pnpm check:all` 按 `scripts/run-gates.ts` 的 windows 子集执行并在交接记录注明。

## 3. 评审与验收机制

1. **双人制**：每个任务的产出由 REV 独立验收（05 §6）；开发代理不得自验。
2. **证据制**：验收只认交接记录六节（05 §7）中的可复核证据——提交号、测试输出摘要、命令回显；"已完成但无证据"一律退回。
3. **检查单**（REV 用，逐条 ✅）：
   - [ ] 改动与任务书范围一致（无搭车改动；范围外→backlog）
   - [ ] 提交序列主题清晰、信息与内容一致
   - [ ] 新增文件有文件头；无本地路径/敏感串
   - [ ] 测试新增且绿；覆盖达标
   - [ ] 对官方文件的改动最小化（`git diff upstream/master...` 抽查）
   - [ ] 无 `as any`/未处理 Promise 新增；无 console 调试残留
   - [ ] i18n：改动文档三元组齐全
   - [ ] 交接记录六节俱全

## 4. 安全红线（SEC 执法，违反即阻断合入）

1. **凭据**：任何 token/密钥不得出现在 remote URL、代码、文档、日志、交接记录；凭据只经凭据管理器。新依赖引入前查其维护状态与已知漏洞。
2. **命令执行**：禁止 `exec`/shell 拼接执行（沙箱内已改 `execFile`，新代码一律 `execFile`/`spawn` 参数数组形态）；危险字符校验保留。
3. **注入面**：禁止 `eval`/`new Function`；动态 import 的路径必须白名单校验。
4. **服务端/工具发起的 URL 请求**：仅允许 `http:`/`https:` 协议；发起前校验目标 host，**拒绝 localhost、环回（127.0.0.0/8、::1）、私有网段（10/8、172.16/12、192.168/16、169.254/16、fc00::/7）与保留地址**（防 SSRF；适用于 web-fetch、插件沙箱网络出口、任何新增取数代码）。本条为验收级要求，相关任务必须附带测试。
5. **信息泄露**：错误消息不得回传堆栈给不可信端；日志脱敏（凭证/路径）沿用既有 obfuscation 手段。
6. **供应链**：不改 `vendor/**` 与 lockfile 指向；新依赖需在交接记录说明理由与许可证（THIRD_PARTY_NOTICES 同步）。

## 5. 文档标准

1. fork 相关文档一律 `docs/dsh/` 下三元组（`.md`+`.zh.md`+`.i18n.yaml`），遵守官方翻译规则与术语表（`docs/i18n/terminology.md`）。
2. CHANGELOG 单一事实源（`docs/dsh/CHANGELOG.md`）；每条带提交号或状态；禁止多版本并行叙事。
3. 根目录不新增过程性报告（过程记录只进 `Plan/logs/` 与 `R&D/archive/`）。
4. 版本叙事统一：只存在"官方版本"与"`<官方版本>-DSH<date><letter>`"两种指称；RC7/8/9 混用不得再现。
