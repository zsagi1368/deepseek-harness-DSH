## 二、Phase 4 新增修复详情

### Fix 1: max-tokens 截断死循环 (NEW-001) 🔴 P0

**问题**: BlockAssembler 在 max-tokens 截断时丢弃最后一个 tool-call，导致 Agent "有意图无执行" 死循环。

**RC9 状态**: assembler.ts 已实现 `truncatedToolCalls` 逻辑，但 **agent.ts 完全没有消费这个字段**。

**RC10 修复**:
```typescript
// packages/core/agent-loop/src/agent.ts:397-418
if (finish.kind === 'max-tokens') {
  if (truncatedToolCalls.length > 0) {
    // 将 truncated tool-call 重新入队，避免死循环
    const toolCalls = truncatedToolCalls.map(block => ({...}))
    this.session.append('assistant/truncated-tool-calls', {...})
    this.inbox.splice('next-step', ...)
    return { kind: 'max-tokens' }
  }
  return { kind: 'max-tokens' }
}
```

**效果**: Agent 在 max-tokens 截断后能继续执行 tool-call，不再死循环。

### Fix 2: contextWindow 配置化 (NEW-002) 🔴 P0

**问题**: agent.ts:341 硬编码 `contextWindow: 32768`，DeepSeek v4 flash 支持 1M tokens，浪费前缀缓存。

**RC10 修复**:
```typescript
// packages/core/agent-loop/src/agent.ts:340-345
const modelContextWindow = preparedCall?.context?.contextWindow ?? 32768
this.session.deriveMessages({ contextWindow: modelContextWindow, minTurns: 3 })
```

**优先级**: catalog 实际值 > cordis.patch.yml 配置 > 模型家族默认值 > 32768 保守默认

## 五、关于"200ms 落盘窗口"的说明

**问题**: ISSUE_INVENTORY E-70 声称 session-persistence-jsonl 的 checkpoint() 异步，turn/end 不等待 flush。

**源码核实**:
```typescript
// packages/session/session-persistence/src/coordinator.ts:30
export const DEFAULT_WRITE_BATCH_MAX_DELAY_MS = 200
```

**结论**: 这是 **intentional design choice**，不是 bug：
- 200ms batch window 平衡了写入性能和持久化保证
- checkpoint() 在 batch 结束时调用，保证数据一致性
- turn/end 事件被包含在 batch 中，不会丢失
- 如需更强持久化，可通过配置调整 `writeBatchMaxDelayMs`

**建议**: 文档化此设计权衡，不修改默认行为。
